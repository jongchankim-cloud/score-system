# score-system 개발 오케스트레이터

## 실행 모드

**서브 에이전트 모드.** 이 환경에는 에이전트 팀 API(`TeamCreate`/`TaskCreate`)가 없으므로 `Agent` 도구로 전문가를 순차·병렬 호출하고, 산출물은 `_workspace/` 파일로 주고받는다.
모든 `Agent` 호출에 `model: "opus"`를 명시한다. 서브 에이전트 호출은 **사용자가 이 워크플로우를 요청했을 때만** 한다.

## 다른 스킬과의 관계

이 저장소에는 범용 프로세스 스킬(`superpowers:brainstorming`, `superpowers:systematic-debugging` 등)도 설치돼 있다. 충돌하지 않는다 — 역할이 다르다.

- 범용 프로세스 스킬이 **어떻게 사고할지**(요구 탐색, 가설 검증 절차)를 정한다면, 이 스킬은 **이 코드베이스에서 누가 무엇을 하는지**를 정한다.
- 요구사항 자체가 불분명한 새 기능이면 `superpowers:brainstorming`으로 먼저 요구를 확정하고, 확정된 요구를 들고 이 스킬의 워크플로우 A로 들어온다.
- 버그의 원인이 코드베이스 지식만으로 안 잡히면 `superpowers:systematic-debugging`의 가설 검증 절차를 `bug-tracer` 안에서 쓴다.
- 반대로, 이 프로젝트 고유의 지식(탭 배치, 복제된 경계면, 운영 데이터 위험)은 범용 스킬에 없다. 그래서 이 스킬을 건너뛰면 안 된다.

## Phase 0 — 컨텍스트 확인

무엇을 하기 전에 상태부터 판별한다.

| 상황 | 실행 모드 |
|------|----------|
| `_workspace/` 없음 | **초기 실행** — Phase 1부터 |
| `_workspace/` 있음 + 부분 수정 요청 | **부분 재실행** — 해당 에이전트만 재호출, 다른 산출물은 유지 |
| `_workspace/` 있음 + 새로운 작업 | **새 실행** — `_workspace/`를 `_workspace_prev/`로 옮기고 초기 실행 |

`_workspace/`는 감사 추적용으로 보존한다. 지우지 말 것.

## Phase 1 — 작업 유형 판별과 규모 판단

요청을 세 갈래 중 하나로 분류한다. 애매하면 사용자에게 묻는다.

| 유형 | 신호 | 워크플로우 |
|------|------|-----------|
| **기능** | "추가", "만들어", "바꿔", "표시" | A |
| **버그** | "안 돼", "이상해", "잘못 나와", 에러 메시지 | B |
| **리팩터링** | "정리", "중복", "리팩터링", "구조" | C |

**규모 판단 — 에이전트를 쓸지 결정한다.**
한 함수 안에서 끝나고 파급이 없는 변경(문구 수정, 색 변경, 조건 하나 추가)이라면 서브 에이전트를 띄우지 말고 직접 처리한 뒤 Phase 4 검증만 수행하라. 에이전트 호출은 공짜가 아니고, 작은 변경에는 정찰 비용이 이득을 넘는다.

에이전트를 쓸 기준: 파급 범위가 불확실하다 · 복제된 경계면(문자 5경로, admin↔index, 삭제 4함수)에 걸린다 · 여러 탭을 건드린다 · 원인을 모른다.

## 워크플로우 A — 기능 추가/변경

```
사용자 요구
  → [1] code-navigator   좌표·파급 범위 특정      → 01_navigator_map.md
  → (요구가 모호하면 여기서 사용자에게 질문)
  → [2] feature-implementer  구현 + 구문 검사     → 02_implementer_report.md
  → [3] regression-qa    회귀 검증                 → 03_qa_verdict.md
  → 결과 보고 + 사용자 확인 항목
```

[1]과 [2] 사이가 중요하다. 정찰이 "요구가 백엔드 변경을 필요로 한다"거나 "요구가 두 가지로 해석된다"고 보고하면 **구현으로 넘기지 말고 사용자에게 먼저 확인한다.**

## 워크플로우 B — 버그 수정

```
증상
  → [1] bug-tracer      원인 특정 (audit-wiring.sh 초반 실행) → 01_tracer_diagnosis.md
  → 원인 미확정이면 → 사용자에게 필요한 정보 요청 후 중단
  → [2] 수정
        사소하면 bug-tracer가 직접, 파급이 크면 feature-implementer  → 02_*_report.md
  → [3] regression-qa   회귀 검증 + 같은 결함의 복제본 확인 → 03_qa_verdict.md
```

원인을 설명하지 못한 상태에서 수정 단계로 넘어가지 않는다. 추측 수정은 증상만 감추고 원인을 남긴다.

## 워크플로우 C — 리팩터링

```
대상
  → [1] code-navigator     복제·중복 지점 전수 조사 → 01_navigator_map.md
  → [2] 사용자에게 범위 제안 및 승인
  → [3] refactor-surgeon   한 종류씩 정리          → 02_refactor_report.md
  → [4] regression-qa      전 범위 검증 (변경 범위가 넓으므로 브라우저 스모크 필수)
```

[2]의 승인 단계를 건너뛰지 않는다. 리팩터링은 사용자가 요청하지 않은 diff를 만들기 쉽고, 테스트가 없어 되돌릴 근거도 약하다.

## 병렬 실행

독립적인 대상이 여러 개일 때만 `run_in_background: true`로 병렬 호출한다.
**같은 파일을 편집하는 에이전트는 절대 병렬로 돌리지 않는다.** 단일 HTML 파일이라 편집이 충돌하면 복구가 어렵다.
병렬이 안전한 경우: 정찰 여러 건, 조사·읽기 작업, 서로 다른 파일 담당.

## 데이터 전달

`_workspace/{순번}_{에이전트}_{산출물}.md` 규약. 반환값은 요약, 상세는 파일.

```
_workspace/
├── 01_navigator_map.md | 01_tracer_diagnosis.md
├── 02_implementer_report.md | 02_refactor_report.md
└── 03_qa_verdict.md
```

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 에이전트 실패 | 1회 재시도. 재실패면 그 단계 없이 진행하고 **최종 보고에 누락을 명시** |
| 정찰이 좌표 특정 실패 | 구현으로 넘기지 않는다. 사용자에게 추가 정보 요청 |
| QA가 실패 판정 | 구현 담당에게 결함을 넘겨 수정 → 재검증. 2회 반복해도 안 되면 사용자에게 상황 보고 |
| 구현과 QA 판단이 상충 | 어느 쪽도 삭제하지 않는다. 양쪽 근거를 병기해 사용자에게 판단 요청 |
| 백엔드 변경 필요 | 프론트 가능 범위까지만 하고, 필요한 백엔드 변경을 명시해 중단 |
| 하위 호환 파괴 필요 | 진행 전 사용자 승인 |

## 운영 데이터 보호 — 예외 없음

이 시스템은 **운영 중인 학원 DB와 실제 SMS 발송**에 연결돼 있다.

- 저장·삭제·문자 발송을 실제로 실행하지 않는다. 브라우저 검증도 읽기 동작만.
- 관리자 비밀번호나 학생 PIN을 요구하지 않는다.
- 마이그레이션·데이터 정정 스크립트를 임의로 만들어 돌리지 않는다.

## 마무리

1. 변경 요약(파일·위치·내용)과 QA 판정을 사용자에게 보고
2. **사용자가 직접 확인해야 할 항목**을 목록으로 제시 (로그인 이후 화면, 실제 저장 동작 등)
3. 커밋은 사용자가 요청할 때만. 메시지는 한국어 + Conventional Commits 접두사
4. 피드백 요청: "결과에서 고칠 부분이나, 이 워크플로우 자체에서 바꾸고 싶은 점이 있나요?"
   피드백이 하네스 구조에 관한 것이면 `harness` 스킬로 에이전트·스킬을 갱신하고 CLAUDE.md 변경 이력에 기록한다.

→ Phase 0 초기 실행 판정 → Phase 1 유형=기능, 규모=에이전트 필요(스키마 컬럼 관련)

→ 만약 감사에 안 걸렸다면: 배제한 가설과 필요한 정보(콘솔 로그·재현 단계)를 적어 사용자에게 요청하고 **추측 수정 없이 중단**
