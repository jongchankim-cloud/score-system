# 단일 파일 HTML 편집

## 전제

`admin.html`(3,913줄)과 `index.html`(1,381줄)은 빌드 단계가 없다. 저장한 파일이 곧 배포물이다.
타입 체커도, 린터도, 테스트도 없으므로 **오타 하나가 런타임에 화면 전체를 죽인다** — `<script>` 하나에 전부 들어 있어 구문 오류 하나면 168개 함수가 모두 정의되지 않는다.
이 제약이 아래 규칙의 이유다.

작업 전 `score-system-map` 스킬로 대상 위치를 먼저 확인하라. 파일을 처음부터 읽지 말 것 — 컨텍스트만 소모한다.

## 편집 순서

1. **grep으로 좌표를 잡는다** — 함수명, DOM id, 클래스명으로 관련 지점을 *전부* 찾는다. 한 곳만 고치고 끝나는 변경은 이 코드베이스에 거의 없다.
2. **주변 30줄을 읽는다** — 들여쓰기, 따옴표 스타일, 헬퍼 사용법을 눈으로 확인한다.
3. **기존 것을 복제해 변형한다** — 비슷한 기능이 이미 있다. 문자 발송 탭을 만들려면 가장 가까운 문자 탭을 그대로 본떠라. 새 패턴을 발명하면 다음 사람이 두 패턴을 다 유지해야 한다.
4. **구문 검증** — 편집 직후 반드시 실행:
   ```bash
   .claude/skills/frontend-regression-qa/scripts/check-syntax.sh
   ```
   인라인 `<script>`를 떼어 `node --check`로 돌린다. 실패하면 다음 단계로 넘어가지 말 것.
5. **경계면 확인** — 아래 "복제된 경계면" 체크.

## 복제된 경계면 — 한쪽만 고치면 조용히 깨진다

이 코드베이스에는 의도적으로 중복된 구현이 세 군데 있다. 수정 대상이 여기 걸리면 **짝을 함께 고치고, 고쳤다는 사실을 결과 보고에 명시하라.**

| 경계면 | 짝 | 어긋나면 |
|--------|-----|---------|
| `ITEM_KEYS` / `DEFAULT_ITEM_CONFIG` / `normalizeItemConfig` / `MOCK_*` | admin.html ↔ index.html | 관리자와 학부모 화면의 점수 해석이 달라짐. 오류 없이 숫자만 틀림 |
| 문자 발송 파이프라인 | 4개 탭 + 미인증 탭 ② | 한 탭만 고쳐지고 나머지는 같은 버그 유지 |
| 삭제 시 외래키 순서 | `deleteClass` / `deleteStudent` / `deleteWeek` / `deleteMockExam` | 새 자식 테이블 추가 시 삭제가 조용히 실패 |

## 관습 (어길 이유가 없으면 지킬 것)

- **전역 `function` 선언 + `onclick` 속성.** 모듈·`addEventListener` 일괄 등록·클래스로 갈아타지 말 것. 절반만 바뀐 코드베이스가 최악이다.
- **데이터 접근은 `api` / `apiRaw` / `apiDelete`만.** 삭제는 예외 없이 `apiDelete` — `api()`는 실패를 삼킨다.
- **색은 CSS 변수로.** `--navy`, `--gold`, `--cream`, `--red`, `--green`, `--orange`와 `-light` 변형. 새 hex를 박지 말 것.
- **버튼은 `.btn` + `.btn-primary`/`.btn-gold`/`.btn-danger`(+`.btn-sm`, `.btn-full`).**
- **알림은 `showToast()`.** 성공 `✅ ...했어요!`, 실패 `❌ ...`. `alert()` 금지, `confirm()`은 되돌릴 수 없는 작업에만.
- **innerHTML에 넣는 사용자 입력은 `escapeHtml` / `escapeAttr` / `attrEsc`를 거친다.**
- **UI 문구는 한국어, 기존 톤 유지.**
- **기존 한국어 주석을 지우지 말 것.** 여러 주석이 과거 버그의 재발 방지 근거를 담고 있다(L854, L862, L1846, L3605 등). 그 코드를 고칠 땐 주석도 함께 갱신하라.
- **탭 전용 전역은 `_접두사`.**

## 하지 말 것

- 파일 전체를 다시 쓰는 편집. 부분 편집만 한다.
- 프레임워크·번들러·npm 의존성 도입. 사용자가 명시적으로 요청하지 않는 한.
- 동작을 "겸사겸사" 개선하기. 요청 범위 밖의 변경은 별도로 제안하고 승인받는다.
- 하위 호환 파괴. `item_config`가 NULL인 과거 주차, `mock_scores.score` 레거시 컬럼은 계속 동작해야 한다.
- 검증 없이 완료 보고. 최소한 구문 검사는 돌린다.

## 리팩터링할 때

동작 보존이 유일한 성공 기준이다.

1. **변경 전 동작을 먼저 문서화한다** — 대상 함수의 입력·출력·부작용을 `_workspace/`에 적어둔다.
2. **한 번에 한 가지만.** 중복 제거와 이름 변경을 같은 커밋에 섞지 말 것.
3. **호출부를 전부 찾았는지 확인한다** — `onclick` 속성 안의 호출은 grep에서 놓치기 쉽다. `onclick="함수명` 패턴으로 따로 검색하라.
4. **추출한 공통 함수가 원본 두 곳 모두의 엣지 케이스를 담는지 확인한다.** 복제 코드는 대개 미묘하게 다르다 — 그 차이가 버그인지 의도인지 먼저 판단하라.
5. 리팩터링 후 `frontend-regression-qa`로 전 범위 검증.
