# 프론트엔드 회귀 검증

## 왜 이 스킬이 필요한가

이 프로젝트에는 타입 체커도, 린터도, 단위 테스트도 없다. 잘못된 코드가 배포되면 조교가 점수를 입력하다 알게 되고, 최악의 경우 학부모에게 틀린 성적 문자가 나간다.
그래서 검증은 "돌려보니 되더라"가 아니라 **정해진 순서로 근거를 남기는 절차**여야 한다.

핵심 원칙: **존재 확인이 아니라 경계면 교차 비교.** 함수가 있는지 보는 게 아니라, 부르는 쪽과 정의하는 쪽·admin 쪽과 index 쪽·저장하는 컬럼과 읽는 컬럼을 **나란히 놓고 비교**한다. 이 프로젝트에서 실제로 터진 버그는 전부 그 경계면에 있었다.

## 실행 순서

앞 단계가 실패하면 뒤 단계는 의미가 없다. 순서대로 진행하고, 각 단계의 **실제 출력**을 결과에 포함하라. 출력 없이 "통과했습니다"라고 쓰지 말 것.

### 1단계 — 구문 검사 (필수, 30초)

```bash
.claude/skills/frontend-regression-qa/scripts/check-syntax.sh
```

인라인 `<script>`를 떼어내 `node --check`로 돌린다.
**실패하면 여기서 멈춘다.** 단일 `<script>`라 구문 오류 하나면 168개 함수가 전부 정의되지 않고 화면이 죽는다.

### 2단계 — 정적 배선 감사 (필수, 30초)

```bash
.claude/skills/frontend-regression-qa/scripts/audit-wiring.sh
```

다섯 가지를 검사한다:
1. `on*=` 속성이 부르는데 정의가 없는 함수 (버튼이 아무 반응 없음)
2. `getElementById`로 읽는데 HTML에 없는 id (`null` 참조 → 그 지점부터 함수 중단)
3. 중복 정의된 함수 (뒤 정의가 앞을 조용히 덮음)
4. 반 선택 select인데 `CLASS_SELECT_IDS` 미등록 (반 목록이 빈 채로 뜸)
5. `ITEM_KEYS` / `DEFAULT_ITEM_CONFIG` / `MOCK_*`의 admin↔index 불일치

결과는 **후보**다. 동적으로 생성되는 id나 핸들러는 오탐이 날 수 있으니 각 항목을 grep으로 확인한 뒤 판정하라.
기존에 이미 존재하던 결함이라면 "내 변경으로 생긴 것이 아님"을 명시하고 별도 보고한다 — 조용히 넘기지도, 요청 없이 고치지도 말 것.

### 3단계 — 변경 경계면 교차 비교 (필수)

`git diff`로 이번에 바뀐 것을 확인하고, 아래 표에서 걸리는 항목만 수행한다.
각 항목은 **양쪽을 동시에 읽고 비교**하는 것이지, 한쪽만 보고 판단하는 게 아니다.

| 변경한 것 | 함께 확인할 반대편 |
|-----------|------------------|
| 점수 컬럼 / `item_config` 관련 심볼 | index.html의 동일 심볼 + 학부모 화면 렌더 경로 |
| `saveAllScores` / `saveMockScores` | 저장 payload의 키 ↔ `references/schema.md`의 컬럼명, 비활성 항목 제외 규칙 유지 여부 |
| 모의고사 점수 저장 | `score` 레거시 컬럼도 합계로 채우는지, `absent=true`면 점수·`retest_pass`가 NULL인지 |
| 문자 발송 로직 한 곳 | 나머지 4곳(`tab-sms`/`absent`/`clinic`/`score-sms`/`uncert`②)이 같은 결함을 공유하는지 |
| 수신처(`phone` vs `student_phone`) | 학부모 발송에 학생 번호가, 학생 발송에 학부모 번호가 섞이지 않는지 |
| 삭제 로직 / 새 자식 테이블 | `deleteClass`·`deleteStudent`·`deleteWeek`·`deleteMockExam` 네 곳의 외래키 순서 전부 |
| DELETE 호출 추가 | `apiDelete`를 썼는지 (`api()`는 실패를 삼킨다) |
| 새 탭 / 새 select | 탭 추가 5개 지점 (`references/tabs.md`) 전부 반영됐는지 |
| innerHTML에 값 삽입 | `escapeHtml`/`escapeAttr`/`attrEsc`를 거쳤는지 |

상세 판정 기준과 과거 사고 사례는 `references/boundary-checks.md` 참조.

### 4단계 — 브라우저 스모크 (동작 변경 시 필수)

UI 동작을 바꿨다면 정적 검사만으로는 부족하다. `claude-in-chrome` 스킬로 실제로 열어 확인한다.

1. `file://` 경로로 해당 HTML을 새 탭에서 연다
2. 콘솔 메시지를 읽어 **에러가 0건**인지 확인한다 (`read_console_messages`)
3. 변경한 화면 경로를 실제로 클릭해 지나간다
4. 스크린샷으로 레이아웃 깨짐을 확인한다

**로그인이 필요한 화면은 사용자에게 비밀번호/PIN을 요구하지 말 것.** 대신 로그인 화면까지만 확인하고, 그 뒤 검증이 필요하면 "관리자 화면에서 직접 확인이 필요한 항목"을 목록으로 넘긴다.
**실제 데이터를 쓰는 저장·삭제·문자 발송 버튼은 절대 누르지 않는다.** 이 시스템은 운영 중인 학원 DB와 실제 SMS에 직결돼 있다. 읽기 동작만 확인하라.

### 5단계 — 판정

```
## 회귀 검증 결과
구문 검사:    통과 / 실패    <실제 출력>

판정: 통과 | 조건부 통과(사용자 확인 필요 항목) | 실패
기존 결함(이번 변경과 무관): ...
사용자가 직접 확인해야 할 것: ...
```

## 하지 말 것

- 검사를 돌리지 않고 통과라고 쓰기. 근거 없는 판정은 검증이 아니다.
- 발견한 결함을 요청 없이 고치기. QA는 보고하고, 수정 여부는 사용자나 구현 담당이 정한다.
- 오탐일 수 있다는 이유로 조용히 빼기. 오탐이면 오탐이라고 근거와 함께 적는다.
- 운영 데이터를 건드리는 버튼 클릭.
